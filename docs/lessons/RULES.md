# כללי תיעוד ליומן הלקחים

היומן (`LESSONS.md` בתיקייה הזו) מרכז תקלות בתהליך הבנייה ושיטות שחוסכות זמן, מכל האפליקציות שנבנות מהתבנית.
המטרה: מי שנתקל בבעיה — סוכן AI או מפתח — מוצא תוך דקה אם היא כבר נפתרה, ומי שפתר בעיה חדשה מוסיף אותה
באותו מבנה בדיוק, בלי כפילויות.
**המקור הוא ריפו התבנית** (`stodio-dev/android-app-template`). באפליקציה יש רק צילום לקריאה בלבד — ראו סעיף 8.

## 1. מתי קוראים
- **בתחילת משימה:** קוראים את טבלת האינדקס בראש `LESSONS.md` בריפו התבנית (קצרה), ופותחים את הרשומות של התחומים
  שהמשימה נוגעת בהם. אם אי אפשר לצרף את התבנית לסשן — קוראים את הצילום המקומי (סעיף 8).
- **כשמשהו נכשל** (build, Actions, פקודה, התקנה בטלפון): לפני שמנסים לתקן, מחפשים ביומן 2–3 מילים ייחודיות
  מהודעת השגיאה (מתוך השכפול של התבנית):
  ```bash
  grep -rn -i "keystore" docs/lessons/
  grep -rn "^### CI-" docs/lessons/        # כל הרשומות של תחום
  ```
- **רשומה היא לא הוכחה.** לפני שמיישמים פתרון מהיומן, בודקים שהוא עדיין מתאים לקבצים הנוכחיים: `build.gradle`
  (גרסת AGP), `gradle/wrapper/gradle-wrapper.properties` (גרסת Gradle) ו־`.github/workflows/build.yml`
  (`java-version`, `runs-on`). גרסאות ששונות מאלה שבשדה `אומת` של הרשומה אומרות שהלקח אולי התיישן.
- **גרסאות בשדה `אומת`:** ברשומות `BUILD`, `CI` ו־`SIGN` רושמים את הגרסאות שהיו בזמן האימות: AGP, Gradle,
  `java-version`, וגרסת ה־runner image מראש ה־log של Actions (בשלב `Set up job`, קבוצת `Runner Image`: השורות
  `Image:` ו־`Version:`). ה־workflow רץ על `ubuntu-latest`, שמשתנה עם הזמן — כך ברור מתי לקח התיישן אחרי שדרוג.
  פורמט: `AGP 8.11.1 · Gradle 9.1.0 · java 21 · ubuntu-26.04/20261101.186.1`.

## 2. מתי כותבים
כותבים רשומה כשמתקיים אחד מאלה:
- **תקלה** שלקחה יותר מניסיון אחד לפתור, או שסביר שתחזור באפליקציה אחרת.
- **שיפור**: שיטת עבודה, פקודה או כלי שחסכו ריצות build, זמן או עלות, ונוסו בפועל.
- **תקלה פתוחה**: build או ריצה שנכשלו בלי סיבה ידועה — דווקא אותן היומן צריך לתפוס. נכתבת עם
  `מצב: פתוח — אין פתרון`: תסמין, שורת השגיאה המדויקת, ומה כבר נוסה ולא עזר. אין בה `סיבה`, `פתרון`, `מניעה`
  או `אומת`, וגם לא השערות:
  ```markdown
  ### CI-004: כותרת — מה נכשל
  - **סוג:** תקלה
  - **חל על:** כל האפליקציות
  - **מצב:** פתוח — אין פתרון
  - **תסמין:** מה רואים, עם שורת השגיאה המדויקת: `error: ...`
  - **נוסה:** מה כבר נוסה ולא עזר, פעולה אחת בכל פריט עם התוצאה
  - **תצפיות:**
    - 2026-11-22, `<owner>/<repo>`, ריצה 123456: מה השתנה מאז הריצה האחרונה שעברה; Re-run בלי שינוי: עבר / נכשל
  - **נצפה:** 2026-11-22 (×1)
  ```
  מי שנתקל באותה שגיאה מוסיף שורת תצפית ומעדכן את `נצפה`, ולא פותח רשומה חדשה. השאלה האחרונה מבדילה בין תקלה
  חולפת (Re-run בלי שינוי עבר) לתקלה אמיתית (נכשל שוב). כשנמצא פתרון: המצב הופך ל־`פעיל`, נוספים `סיבה`,
  `פתרון`, `מניעה` ו־`אומת`, והתצפיות נשארות.

לא כותבים:
- טעות הקלדה חד־פעמית, או משהו שכבר כתוב ב־`CLAUDE.md` / `README.he.md` (אם הכלל שם חסר או לא ברור — מתקנים שם).
- השערות שלא נבדקו. מה שלא אומת נכתב רק עם `מצב: לא אומת`, ועדיף לא בכלל. (תקלה בלי פתרון היא לא השערה:
  נכתבת כתקלה פתוחה, למעלה.)

## 3. מניעת כפילויות (חובה לפני כל רשומה חדשה)
1. מחפשים לפי הודעת השגיאה (מילים ייחודיות, בלי מספרי שורות, נתיבים או שמות חבילה של אפליקציה מסוימת).
2. מחפשים לפי התחום (`^### <תחום>-`) ולפי מילות מפתח של הפתרון.
3. **נמצאה רשומה על אותה בעיה** ← מעדכנים אותה ולא פותחים חדשה: מוסיפים את הווריאנט לשורת התסמין, משפרים את
   הפתרון, ומעדכנים את שורת `נצפה` (תאריך אחרון ומונה: `2026-11-22 (×3)`).
4. **חפיפה חלקית** (אותה סיבה, תסמין אחר — או להפך) ← רשומה חדשה, ושורת `ראו גם:` בשתי הרשומות.
5. **רשומה שהתבררה כשגויה או שכבר לא נכונה** ← לא מוחקים. משנים ל־`מצב: מיושן — ראו <מזהה>` ומשאירים את התוכן.
6. כל רשומה חדשה מקבלת גם שורה בטבלת האינדקס, באותו commit.

## 4. מבנה רשומה
כל רשומה היא כותרת `###` ואחריה השדות בסדר הזה בדיוק. שדה שלא רלוונטי (למשל `תסמין` בשיפור) — משמיטים.

```markdown
### CI-001: כותרת קצרה — מה נשבר או מה משתפר
- **סוג:** תקלה | שיפור
- **חל על:** כל האפליקציות
- **מצב:** פעיל
- **תסמין:** מה רואים, עם שורת השגיאה המכרעת מילה במילה: `error: ...`
- **סיבה:** למה זה קורה (משפט או שניים)
- **פתרון:** מה עושים — פקודה או שינוי מדויקים, לא הסבר כללי
- **מניעה:** מה עושים מראש כדי שזה לא יקרה שוב (בדיקה, צעד בתהליך, שינוי בתבנית)
- **אומת:** איך יודעים שהפתרון עובד (ריצת Actions, `core-tests`, בדיקה בטלפון, שחזור) + תאריך; ב־BUILD/CI/SIGN גם גרסאות (סעיף 1)
- **ראו גם:** BUILD-002
- **נצפה:** 2026-11-22 (×1)
```

שדות נוספים רק בשני מקרים, ותמיד לפני `נצפה`: `נוסה` ו־`תצפיות` בתקלה פתוחה (סעיף 2), ו־`מקור` או `בתבנית`
ברשומה שהועברה בין ריפואים (סעיף 8).

## 5. מזהים
- פורמט: `<תחום>-<מספר בן 3 ספרות>`, למשל `CI-003`. המספר הבא הפנוי באותו תחום.
- מזהה לא משתנה ולא ממוחזר, גם כשהרשומה מתיישנת — רשומות אחרות ו־commits מפנים אליו.
- הרשומות ב־`LESSONS.md` (או בקבצי התחומים, אחרי פיצול — סעיף 7) מסודרות לפי תחום, בסדר הטבלה למטה, ובתוך
  תחום לפי מספר.

| תחום | מה נכנס |
|---|---|
| `BUILD` | Gradle, AGP, קומפילציה, משאבים (`res/`), manifest |
| `CI` | GitHub Actions, סודות (secrets), שחרור `latest`, הורדת ה־APK |
| `SIGN` | חתימה, התקנה מעל גרסה קודמת, `app.signer` |
| `JAVA` | רמת שפה, תחביר, `core` ו־`core-tests` |
| `API` | ממשקי אנדרואיד: גרסאות, הרשאות, מחזור חיים של Activity, שירותים |
| `UI` | מסכים, עברית ו־RTL, פריסה, insets, נגישות |
| `GFX` | Canvas, OpenGL, אנימציה, משחקים |
| `NET` | רשת, APIs חיצוניים, מפתחות API |
| `DATA` | העדפות, קבצים, מסד נתונים, גיבוי |
| `PERF` | ביצועים, סוללה, זיכרון, גודל APK |
| `TEST` | בדיקות, דיבוג בלי גישה לטלפון (יומן, דוח קריסה) |
| `APP` | לקח שייחודי לאפליקציה אחת: נכתב רק ב־`docs/lessons/APP.md` באפליקציה ולא בתבנית (סעיף 8). שאר התחומים בטבלה הם של התבנית |
| `PROC` | תהליך עבודה: סשנים בענן, git, ענפים, הרשאות, תקשורת עם המשתמש |

## 6. ערכים קבועים
- **סוג:** `תקלה` או `שיפור`.
- **חל על:** אחד או יותר מ: `כל האפליקציות`, `סשן ענן`, `משחקים / גרפיקה`, `אפליקציות רשת`, `מצלמה / מדיה`,
  `רקע / התראות`, `אחסון נתונים` — או `אפליקציה: <שם הריפו>` כשזה באמת ייחודי לאפליקציה אחת.
- **מצב:**
  - `פעיל` — רלוונטי, צריך לפעול לפיו.
  - `תוקן בתבנית (<commit קצר>, <YYYY-MM-DD>)` — התבנית עצמה תוקנה; רלוונטי רק לאפליקציות שנוצרו לפני התיקון:
    אפליקציה עם `template.date` מוקדם מהתאריך הזה (ב־`gradle.properties`), או בלי `template.date`, צריכה להחיל את התיקון
    בעצמה; אפליקציה שנוצרה אחריו כבר כוללת אותו.
  - `מיושן — ראו <מזהה>` — כבר לא נכון.
  - `לא אומת` — נצפה אבל הפתרון לא נבדק עד הסוף.
  - `פתוח — אין פתרון` — תקלה שנצפתה ולא הוסברה; בלי סיבה ופתרון, עם `נוסה` ו־`תצפיות` (סעיף 2).
  - `הפך לכלל ב־CLAUDE.md (<כותרת הסעיף>)` — הלקח עבר לכלל קבוע (סעיף 8); הרשומה נשארת להקשר.

## 7. סגנון
- **שפה:** עברית. הודעות שגיאה, פקודות, נתיבים, שמות API ושמות שלבים ב־Actions — באנגלית, מילה במילה, בתוך `קוד`.
- **קצר:** עד כ־12 שורות לרשומה. פקודה או diff קטן עדיפים על פסקה. לוג ארוך — רק השורה המכרעת.
- **כללי:** כותבים כך שיתאים לכל אפליקציה מהתבנית: `<package>`, `<owner>/<repo>`, `<ApkName>` במקום שמות אמיתיים.
  פרטי האפליקציה שבה זה קרה — רק בשורת `אומת`, כדוגמה.
- **תאריכים:** `YYYY-MM-DD`.
- **גודל:** כש־`LESSONS.md` עובר בערך 400 שורות, מפצלים אותו לקובץ לכל תחום (`docs/lessons/BUILD.md`, `CI.md`
  וכו'). טבלת האינדקס נשארת ב־`LESSONS.md` עם קישור לקובץ של כל תחום, והמזהים לא משתנים. החיפוש בסעיף 1 רץ על
  כל התיקייה, כך שהוא עובד לפני הפיצול ואחריו.
- **אסור לכתוב:** מפתחות API, סיסמאות, ערך ה־keystore או ה־base64 שלו, טוקנים, כתובות מייל, מידע אישי, כתובות
  פנימיות. במקומם: `<API_KEY>`, `<owner>`.

## 8. בין התבנית לאפליקציות
- **מקור אחד: ריפו התבנית** (`stodio-dev/android-app-template`, התיקייה `docs/lessons/`). הוא רשום ב־`template.repo`
  ב־`gradle.properties` של האפליקציה (אפליקציה ישנה בלי השדה משתמשת בשם הזה). סוכן שעובד על אפליקציה מצרף את התבנית
  לסשן (`add_repo`, `access: "push"`; ייתכן שהמשתמש יתבקש לאשר), משכפל אותה לתיקייה מחוץ לריפו האפליקציה, קורא ממנה
  וכותב אליה.
- **מה נכתב בתבנית:** כל רשומה עם `חל על: כל האפליקציות`, `סשן ענן` או סוג אפליקציות (משחקים, רשת וכו'). המזהה הוא
  המספר הפנוי בתבנית. לפני הכתיבה: `git pull --rebase`, בדיקת כפילויות (סעיף 3), ואחרי העריכה דוחפים מיד. אם צצה
  התנגשות בטבלת האינדקס — שומרים את שני הצדדים ובודקים ב־`grep` שאין מזהים כפולים. מסשן של אפליקציה נוגעים בתבנית רק
  בקבצים שתחת `docs/lessons/`; תיקון בקוד, בסקריפט או ב־workflow שלה — המשתמש מבקש.
- **מה נשאר באפליקציה:** רשומה עם `חל על: אפליקציה: <שם הריפו>` נכתבת ב־`docs/lessons/APP.md` באפליקציה, באותו
  פורמט, עם מזהים `APP-001` וכן הלאה (הם לא מתנגשים עם מזהי התבנית).
- **אי אפשר לצרף את התבנית** (הכלי לא זמין, נדחה או אין הרשאה): כותבים את הרשומה בפורמט המלא ל־`docs/lessons/PENDING.md`
  באפליקציה, ומודיעים למשתמש בסוף העבודה. סשן מאוחר עם גישה מעביר אותה לתבנית (בדיקת כפילויות, מזהה פנוי שם) ומוחק
  אותה מ־`PENDING.md`.
- **הצילום המקומי:** `new-app.sh` משאיר באפליקציה את `LESSONS.md` ו־`RULES.md` כצילום (`README.md` בתיקייה אומר מאיזה
  תאריך). הוא לקריאה בלבד, גיבוי כשאין גישה למקור. לא כותבים בו, והוא לא מתעדכן: את הגרסה העדכנית קוראים מהתבנית.
- **העברה חד־פעמית:** רשומה שנכתבה בצילום של אפליקציה ישנה, מלפני המודל הזה, מועברת לתבנית פעם אחת. בהעברה מוסיפים
  שדה הצלבה בשתי הרשומות: בתבנית `- **מקור:** <owner>/<repo> <מזהה>`, ובאפליקציה `- **בתבנית:** <מזהה>`.
- כשלקח מוביל לתיקון בתבנית עצמה (סקריפט, workflow, קוד בסיס) — מתקנים, ומעדכנים את הרשומה ל־`תוקן בתבנית (<commit>,
  <YYYY-MM-DD>)` (סעיף 6).
- **לקח שחוזר הופך לכלל או לתיקון.** כשהמונה `נצפה` מגיע ל־×3, או כשהלקח נוגע לכל סשן, מעבירים אותו לכלל
  ב־`CLAUDE.md` או לתיקון בתבנית (סקריפט או workflow), ומשאירים ברשומה הפניה במצב: `הפך לכלל ב־CLAUDE.md (...)`
  או `תוקן בתבנית (...)`. אחרת לקח חשוב נקבר בתוך היומן.
